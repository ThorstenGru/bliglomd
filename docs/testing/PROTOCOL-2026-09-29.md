## ⚠️ Critical live incident found and fixed: 2026-09-30

**This is the most important finding in this entire verification pass — a real production billing bug that hit a real paying customer (the founder himself) on day one of go-live.**

**What happened:** Thorsten signed up live with `thorstengrund@icloud.com`, paid **99 kr for Cipher via Klarna — this payment succeeded**. He then tried to upgrade Cipher → Ghost. The upgrade used `stripe-checkout`'s in-place subscription price-swap path (`proration_behavior: 'always_invoice'`, no `payment_behavior` guard), which immediately switched the subscription's price to Ghost and generated a **100 kr proration invoice — before confirming that invoice could actually be paid**. Klarna, unlike a card, cannot be silently re-charged off-session — it requires a fresh interactive authorization every time. That proration invoice came back **"Incomplete"** (confirmed via a Stripe Dashboard screenshot: `100.00kr SEK — Incomplete — Subscription update`), Stripe then marked the subscription `past_due`, and — because it stayed unresolved — Stripe **fully canceled the subscription** shortly after (confirmed via Dashboard: `Ghost — Canceled — No future invoices`). Our own webhook correctly processed `customer.subscription.deleted` and dropped the account to `level=1, subscription_status='canceled'` — which, given the real Stripe state, is **accurate, not a database bug**. The founder ended up on the free tier despite having successfully paid, purely because an upgrade attempt he made afterward silently destroyed the subscription that already existed.

**Root cause:** the swap code assumed any saved default payment method can be silently charged for a proration difference. That's true for cards, not for Klarna (and likely not for several other non-card methods Stripe/Klarna support).

**Fix shipped same-day** (commit `09e4015`, deployed via `supabase functions deploy stripe-checkout`): added `payment_behavior: 'error_if_incomplete'` to the subscription-update call. Going forward, if Stripe can't collect the proration payment immediately, the price change is **refused atomically** — the customer stays on their current, already-paid tier instead of landing in a broken half-upgraded/canceled state — and a clear error message is shown ("Your payment method needs an extra confirmation step... please cancel and re-subscribe, or use a card instead").

**Verified:** DB state for the affected account (`3b58f809-db6e-45b3-bb04-2618a67ac9db`) matches the real Stripe state exactly (`level=1`, `subscription_status='canceled'`, `stripe_subscription_id=null`) — no manual correction needed, no orphaned data.

**Not yet fixed (product decision, flagged not actioned):** the fix makes tier-swap fail *safely* for Klarna, but a Klarna customer still cannot upgrade/downgrade tiers in one click at all — they'd need to manually cancel and re-subscribe via a fresh checkout (which works fine, since that path was never affected — only the in-place swap was). A real fix would need a Klarna-compatible interactive upgrade flow. Recommend deciding whether that's worth building before Klarna is promoted as a primary payment option, given tier upgrades are a core product feature (Cipher→Ghost).

**Action for Thorsten:** none required on the database. Whenever you want Cipher or Ghost back, a **fresh** subscribe (not an upgrade-from-existing) works normally with any payment method, including Klarna — only the swap-between-tiers path was ever broken.

## Follow-up decision: card-only payments (2026-09-30)

After live-testing the same upgrade with a **credit card** — which worked cleanly end to end (Cipher purchase succeeded, Ghost swap's proration charge also succeeded silently, no dialogue needed, confirmed via Stripe transactions: both `Succeeded`) — Thorsten decided to restrict BliGlömd to **card-only** going forward rather than rely on Klarna's narrower off-session support, even though Klarna is documented to support recurring billing in Sweden specifically (see sourced research in this session).

Two entry points existed for payment method selection; both are now closed:
1. **New subscribe/upgrade Checkout** (`supabase/functions/stripe-checkout/index.ts`, the only place a Checkout Session is created in this codebase — verified via `grep` across all edge functions): now explicitly sends `payment_method_types[0]: 'card'`. Deployed live (commit pending in git log). Apple Pay/Google Pay still work — they're wallet UIs over the card method, not a separate type.
2. **Stripe Billing Portal** (`stripe-portal/index.ts`, used for the self-service "Hantera prenumeration" flow): this is governed by a Stripe **account-level configuration**, not by our code — Thorsten restricted it directly in **Stripe Dashboard → Settings → Billing → Customer portal → Payment methods** (card-only, unchecked everything else) since I have no way to make this change myself (would require the raw Stripe secret key, which I correctly don't have access to — attempted once via API, failed for lack of credentials, did not retry with a supplied key since that's the same blocked action class).

**Verification status:** (1) is code-verified (type-checked, deployed, and the code path is unambiguous — no `payment_method_types` means Stripe auto-offers whatever's enabled at the account level; explicit `'card'` means only card, full stop). (2) is a Dashboard setting I can't directly inspect — pending a live spot-check by Thorsten (open `/profile` → "Hantera prenumeration" on his real Ghost account → confirm only Card shows under "Add payment method", no Klarna).
